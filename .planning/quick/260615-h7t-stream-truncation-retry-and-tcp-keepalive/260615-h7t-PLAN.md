# Quick Task 260615-h7t: Stop losing work when a gateway silently drops a quiet stream

## Problem (reported)

Behind a corporate/office gateway, long agent requests "hang" — the client shows
running but receives nothing, forcing repeated Ctrl+C + "continue". At home (no
gateway) it never happens. The drop lands during long reasoning, i.e. when the
byte stream goes quiet. Topology:

```
agent → [9router on office server] → [GATEWAY] → provider
```

The gateway sits on the upstream hop. When the provider stream goes quiet during
reasoning, the gateway reaps the idle connection WITHOUT a clean close (half-open
TCP drop). 9router is the reader on that hop, so it can't heartbeat it.

## Root cause (verified in code)

`open-sse/utils/streamHandler.js` → `createDisconnectAwareStream`: when the
upstream socket reset (ECONNRESET/ETIMEDOUT/socket hang up) OR the stall watchdog
fired (`pipeWithDisconnect` → `handleError` → `isConnected()` false), the code
called `controller.close()` — a GRACEFUL end-of-stream — for all non-Responses
streams. So a TRUNCATED stream was indistinguishable from a COMPLETED one. The
client SDK saw a clean EOF, assumed success, and never retried → lost tokens,
time, and context.

Stall/timeout knobs already existed and are env-tunable (`STREAM_STALL_TIMEOUT_MS`
default 360s, `FETCH_CONNECT_TIMEOUT_MS` 60s) but only converted an infinite hang
into a *silent* short close — they did not make the client retry.

## Tasks

### Task 1 — Distinguish truncation from clean completion (the lost-work fix)
- files: `open-sse/utils/streamHandler.js`
- action: In `createDisconnectAwareStream`, scan forwarded bytes for a provider
  terminal marker (`[DONE]`, `message_stop`, real `finish_reason`,
  `response.completed/failed`, Ollama `done:true`) with a 32-char tail carry-over
  for split chunks. On a transport reset / stall-abort:
  - client cancelled OR a terminal marker already seen → graceful `close()`
    (data is complete; reset is just teardown).
  - Responses passthrough (`onAbortTerminal` set) → keep synthesizing
    `response.failed` + `[DONE]` (existing behavior, now centralized).
  - otherwise (genuine truncation, no terminal) → `controller.error()` so the
    client SDK sees a broken stream and retries.
- verify: unit tests for each branch.
- done: a mid-reasoning gateway drop surfaces as an error → agent retries instead
  of silently receiving nothing.

### Task 2 — TCP keepalive on the upstream socket
- files: `open-sse/utils/proxyFetch.js`, `open-sse/config/runtimeConfig.js`
- action: Add `UPSTREAM_TCP_KEEPALIVE_MS` (default 20000, 0=disable). Apply
  `SO_KEEPALIVE` via an undici custom connector on the direct dispatcher and the
  HTTP ProxyAgent, and via `socket.setKeepAlive` on the manual MITM-bypass socket.
- verify: undici connector probe confirms `setKeepAlive` works on the TLS socket
  (undici 7.27); fetch still succeeds.
- done: an L3/L4 firewall/NAT sees keepalive probes and keeps a quiet flow alive.
- caveat: ineffective against an L7 filtering proxy (Zscaler/Blue Coat/Palo Alto)
  that counts application bytes — Task 1 is the safety net there.

### Task 3 — Tests
- files: `tests/unit/stream-truncation.test.js` (new),
  `tests/unit/responses-abort-terminal.test.js` (updated to new contract)
- done: truncation→error, complete-then-reset→graceful, client-cancel→graceful,
  Responses→structured terminal, finish_reason:null≠terminal, split-marker.

## Scope guard
Shared streaming path → all providers benefit identically. No provider-specific
branching. Stall/connect timeouts unchanged (already tunable). Keepalive is
best-effort and fully disablable. Operator can also set
`STREAM_STALL_TIMEOUT_MS=45000` to fail fast instead of waiting the 6-min default.
